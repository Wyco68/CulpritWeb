01 How Requests Flow

Every API call follows the same path: a route handler checks who's asking and whether the input is valid, a service applies the actual business rules, and a repository is the only place that talks to the database. Each layer only knows about the one below it. This keeps rules easy to find: if it's about permissions or input shape, it's in the route handler; if it's a business rule, it's in the service.

02 Appointments

There is no request-and-approve workflow. The admin creates an appointment directly from the admin dashboard, that's it. An appointment can only move from "scheduled" to "cancelled", and cancelling never deletes the row, it just marks it. The app doesn't send any email for appointments; if a visitor books through the Calendly widget, Calendly sends its own confirmation and that booking never becomes a row in this app's database at all. Every change made through the admin, including a cancellation, gets written to an audit log in the same database transaction as the change itself.

03 Calendly

Calendly is embedded on the "Make Appointment" page and nowhere else. There is no server-side connection to Calendly: no API token, no webhook, no syncing bookings back into this app's database. A visitor books directly in the widget, Calendly handles the confirmation, and that's the end of the app's involvement.

If a Calendly booking should show up on the public "Upcoming Events" tab, the admin adds it by hand. Calendly has no free-tier way to push a booking into another system automatically, so this is a deliberate choice, not a missing feature.

04 Caching

Caching means keeping a saved copy of something so the next request doesn't have to redo the work. Done carelessly it also means someone can see an old version of a page after it's changed, so this runs through three layers, each with its own job: the visitor's browser, Cloudflare at the edge, and Next.js on the server. A request only reaches the next layer down if the one above it doesn't already have a fresh copy.

ContentBrowserCloudflare / server
Images, JS, CSS files1 year1 year
Public pages (Bio, Research, etc.)—1 hour
Research / publications / profile / team-member data5 minutes1 hour
Upcoming-events data1 minute5 minutes
Anything behind admin loginnevernever

Upcoming events gets a shorter cache time on purpose: an appointment can slip from "upcoming" into "in the past" while nobody's looking, so a shorter window limits how long a stale, already-past event could keep showing.

The moment an admin save succeeds, the app clears its own server cache for the affected pages right away, and, where set up, tells Cloudflare to drop its cached copy too. In practice a real edit shows up within a second or two — the TTLs above are a safety net for the rare case where content changes some other way that skips this process (a direct database edit, for example), not the primary way freshness is kept.

A subtlety worth knowing, because it caused a real bug: Next.js marks its responses with a Vary header saying "this page can look different depending on certain request headers," for the background fetch it does on client-side navigation. Cloudflare ignores that header by default. Turning on edge caching without accounting for it would let a normal page load and a background navigation fetch collide in the same cache slot. That was caught and fixed by explicitly telling Cloudflare to keep those two request types in separate cache entries — not something that would be obvious without checking.

05 Security & Abuse Protection

Rate limiting

Two things are protected: the admin login, and admin save/edit/delete actions. Both go through two layers. First, Cloudflare blocks more than 5 login attempts in 10 seconds at the edge, before the request ever reaches the app server — this is the main defense. Behind that, the app keeps its own backup counter (5 login attempts per minute, 30 admin actions per minute) in case the Cloudflare rule is ever off or misconfigured. Two layers exist because Cloudflare's free plan only allows one such rule per site; if that one rule ever fails, the app still protects itself, just a bit more loosely. Public pages aren't rate-limited at all — they're already served from cache, so visiting them repeatedly can't cause any harm.

Turnstile — proving a visitor is a real person

Turnstile is Cloudflare's bot check, and it protects exactly one thing here: the booking calendar on the "Make Appointment" page. Calendly's free plan has no bot protection of its own, so without this check a script could spam-book every open slot on the professor's real calendar. The flow: the visitor's browser gets a one-time code from Cloudflare (usually instant and invisible), the app's server takes that code and asks Cloudflare directly whether it's real, and only once the server gets a yes does the actual booking widget appear. The client-side check alone proves nothing — a fake one could be scripted too — which is why the server-side confirmation is the part that actually gates anything. The code expires in 5 minutes and works once, so it can't be captured and reused.

Everything else

  • All input is validated on the server, not just in the browser. A request can't skip validation by going around the visible form.
  • Every admin endpoint checks the login session on its own; nothing assumes an earlier check already covered it.
  • Secrets like database credentials and API keys never reach the browser.

06 Testing

Automated tests (Vitest) cover the services, validation rules, and components, and run on every push. A separate set of Playwright tests covers full browser flows but isn't wired into that automatic check yet, so it has to be run by hand for now.
