PROJECT_SPEC — "The Culprit"

Personal academic website + direct Calendly booking & appointment-request system for an information-security professor.
Status: v1.0 — In development Owner: Project team Calendly: Free + direct booking Slot: 30 min Auth: Single admin

01 Project Overview

"The Culprit" is a personal academic website for a professor whose field is information security. It presents the professor's work publicly and lets visitors book directly against her live availability, or submit a request the admin reviews.

The product has two halves:

  • Public info — bio, research, publications, and research groups (incl. visiting professors). Design reference: the UCL profile of Lorenzo Cavallaro.
  • Appointment system — a visitor books directly against live availability via the embedded Calendly widget (30-min default), or submits a request stored as pending that the admin approves or declines. When booking, the visitor names which research group they represent, so the admin sees which groups are due to meet. Cancellations are kept as records, never deleted.

Design language: professional, minimalist, information-security aesthetic. See §9 for the current (2026-08-05) Figma-derived visual system: fixed dark-navy header, mono numbered indices, colored-dot status badges.

Elevator pitch: A clean public presence for a security researcher, plus a lightweight, admin-controlled meeting-request workflow that keeps a full audit trail of every request.

02 Goals & Non-Goals

Goals

  • G1 — Professional, minimalist public presence (bio, research, publications, groups).
  • G2 — Visitors book directly (30-min default) or request a meeting, no account (name + email only).
  • G3 — Admin fully controls: approve, decline, cancel requests; edit all content.
  • G4 — Durable record of every appointment (direct or request) + status change (cancellations soft, retained).
  • G5 — Integrate the Calendly widget for direct booking against availability.
  • G6 — Clean, modular architecture reusable across future apps.

Non-Goals

  • NG1 — Direct booking is handled by the Calendly widget itself; the app does not auto-create a Calendly event from a pending request (that path stays manual). No Calendly API supports programmatic booking creation on any plan, so this remains true even after the REST integration below.
  • NG2 — No real-time Calendly sync / webhooks in the MVP Superseded (2026-08-02): a server-side Calendly REST integration was built ahead of schedule (read event-types/scheduled events/availability, admin-triggered cancel that drives the local status machine, and a signature-verified idempotent webhook receiver for invitee.created/invitee.canceled) — see §14.2. Scoped to read + cancel + webhook-receive; does not include auto-book/create-booking, which stays out of scope since Calendly has no public API for it on any plan. Webhook subscription itself may still require a paid Calendly plan; the receiver is built and ready regardless.
  • NG3 — No public user accounts / logins / visitor profiles.
  • NG4 — No multi-admin, no per-researcher self-editing in MVP (single admin).
  • NG5 — No payments, chat, or extra content-approval workflows.

03 Scope

In Scope (MVP)

  • Public site: About, Research, Publications, Team Members, Upcoming Events (admin-gated), Make Appointment (current 6-tab layout, see §9.1 note, 2026-08-05).
  • Research groups & visiting professors (CV-style: works & achievements), via Team Members.
  • Direct Calendly booking (→ booked) and request form (→ pending); requester names their research group.
  • Admin panel: Set Information + Manage Appointments.
  • Lifecycle: direct → booked; request pending → approved → booked, plus declined and cancelled.
  • Embedded free Calendly widget; single admin auth; notification emails.

Out of Scope / Future

  • F1 — Paid-Calendly auto-book + webhook sync.
  • F2 — Multiple admins / roles; researcher self-service editing.
  • F3 — Public search / tagging / filtering of publications.
  • F4 — Analytics dashboard, multi-language.
  • F5 — Native mobile apps.

10 Workflows

10.1 Appointment lifecycle

  1. Direct path: Visitor picks a slot in the embedded Calendly widget (30-min default), names their research group → recorded as booked (source=direct), visitor emailed. (Steps below are the request path.)
  2. Visitor opens Make Appointment, fills the request form (incl. research group), submits.
  3. System stores pending, emails "request received", shows "pending".
  4. Admin opens Manage Appointments, reviews.
  5. Approve → approved, visitor emailed. or Decline → declined, emailed, nothing booked.
  6. For approved: admin manually creates the Calendly event, then Mark booked → booked, event ref saved, visitor emailed.
  7. Cancellation: admin or visitor (unique link) cancels → cancelled, reason recorded, emailed. Record retained.

10.2 Content edit

  1. Admin opens Set Information, edits a form.
  2. Clicks Save changes → API validates and persists → success feedback.

10.3 Upcoming-events visibility toggle

  1. Admin toggles visibility in Set Information.
  2. Public Upcoming Events tab shows or hides accordingly.

12 Architecture

Principle: clean, modular, layered architecture with clear boundaries, reusable consistently across future apps.

12.1 Layers

Note (2026-08-05): stack now concrete, not stack-agnostic aspiration — see §14.1. DB is Supabase Postgres; object store is Supabase Storage (buckets profile, research, publications, events public-read; documents private/signed-URL). YouTube is the exclusive video host (src/modules/integrations/youtube/) — no video bytes ever touch Supabase Storage; the integration is built but not yet wired to any content model (no DB field stores a video ID today).

12.2 Module boundaries

  • content — profile, research, publications, research-groups (incl. TeamMember) (read public, write admin).
  • appointments — request intake, status machine, audit trail.
  • auth — single-admin session management (Better Auth, DB-backed cookie sessions).
  • settings — feature flags (e.g. upcoming-events visibility).
  • notifications — email on status transitions.
  • integrations — Calendly (embed + server-only REST client + webhook receiver), Supabase Storage adapter, YouTube embed helper, email provider.

12.3 Cross-cutting

  • Validation + rate-limiting at the API edge.
  • Audit logging in the service layer.
  • Stack-agnostic — concrete vendors chosen later (see Appendix).

14.1 Stack (adopted)

14.2 Calendly capability (free vs paid)

CapabilityFree plan
See upcoming meetings✅
Cancel a meeting✅
Simple booking widget (embed)✅
Read event types / availability via REST API✅
Cancel a meeting via REST API (syncs local status)✅
Receive webhooks (invitee.created / invitee.canceled)✅ built, ⚠️ subscribing may need paid
Auto-book / create a booking via API❌ no public API on any plan
Takeaway: direct visitor booking still uses the free embedded widget. Adopted deviation (2026-08-02): a full server-side Calendly REST integration was built: a PAT-authenticated client reading event types, scheduled events, and availability; an admin cancel endpoint that also drives the local appointment state machine; and a signature-verified, idempotent webhook receiver for invitee.created/invitee.canceled (unique on calendlyInviteeUri). This supersedes NG2's "no webhooks/sync in MVP" ahead of schedule, scoped to read + cancel + webhook-receive. What remains genuinely unavailable, and does not change even on a paid plan, is programmatic booking creation: Calendly does not expose that endpoint on any plan, so createBooking() honestly reports { supported: false, reason, schedulingUrl } instead of faking it. The in-app request path (pending → approved) still requires the admin to manually book the meeting in the embedded widget and mark it booked. Webhook subscription itself may still require a paid Calendly plan per Calendly's plan matrix; the receiver is implemented and ready regardless. See src/modules/integrations/calendly/README.md for the full capability list and rationale.
