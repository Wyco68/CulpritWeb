Why this one, now

  • Option 1 is not available at any price we'd recommend paying. The repository now lives under the culpritteam GitHub organisation. Vercel refused to import it under the free Hobby plan: deploying a repo owned by an organisation requires being a member of a paid Vercel Team, from $20 a month. That's on top of the browser rebuild the first report already priced in. We stopped pursuing it. Detail in section 2.
  • Option 2 works, but its free database has two real gaps. Supabase's free plan takes no automatic backups, and a project with no traffic for a week pauses until someone manually resumes it. Closing both gaps costs $25 a month for Supabase Pro, at which point Option 2's price advantage over a dedicated server has mostly disappeared.
  • A dedicated server gets its own database, and the backup comes free with it. Postgres runs on the same machine as the app; a nightly pg_dump to the same Cloudflare R2 bucket already wired up for photo storage costs $0 in fees, because the app already ships the S3 client that writes to it. No pause-on-inactivity rule applies to a database you run yourself.
  • Nothing gets rebuilt, again. Option 3 runs the exact same Docker image and deploy script already built for Option 2: moving from one to the other is a bigger server and a one-time database migration, not new development.
  • Only two suppliers ever send an invoice, and one of them is a $12-a-year domain. Supabase drops off the bill entirely.

3The three decisions we need from you Each one states what we propose, what it risks, and what the alternative costs.

Decision 1  ·  Move the database off Supabase's free plan and onto the dedicated server itself?

Today's database (Option 2, live) is Supabase's free plan. It takes no automatic backups, and, separately, a Supabase project with no traffic for a week pauses itself until manually resumed from the dashboard. Neither is a hypothetical: it's stated on Supabase's own free-tier terms.

What moving fixes. A self-hosted Postgres database on the dedicated server has no such pause rule; the server runs whether or not anyone visits that week. A nightly backup job (pg_dump, piped to the same Cloudflare R2 bucket already configured for photo storage via the app's existing S3 client) costs $0 in fees. Reaching the same safety on Supabase costs $25 a month (฿828) forever, via Supabase Pro.

We propose: move to Option 3. What it costs: the $12–15/mo gap between the two servers, minus the $25/mo Supabase Pro would otherwise cost to reach equal safety. Net, this is the cheaper way to get a backed-up database, not the more expensive one. If you would rather not: stay on Option 2 and accept the pause risk, or pay $25/mo for Supabase Pro on top of Option 2's server cost.
Decision 2  ·  Keep photos and PDFs on Cloudflare R2, or move them onto the dedicated server's own disk?

R2 is already built, already free, and never charges for sending files to visitors. The full comparison is in section 7. A dedicated server can hold files on its own disk instead, which is what "its own database and its own storage" means as a capability. Whether to actually use that capability for files is a separate question from whether to use it for the database.

We propose: keep files on R2. Why: it costs nothing today, it's already integrated, and self-hosting file storage would mean building our own backup and delivery path for something R2 already does free, with no visitor-facing benefit. If you'd rather consolidate to one provider anyway: moving is possible later without touching the database decision; they're independent.
Decision 3  ·  Buy one domain, used for both the web address and the email?

Unchanged from the last report. A single domain at about $12 a year (฿397) does two jobs: the address visitors type, and the "from" address on the emails the site itself sends, most importantly the verification code the admin needs to log in. Resend's free plan ties 3,000 emails a month to one domain per account; without our own, that allowance is shared with whatever else runs on the same account.

We propose: buy one domain. If you would rather not: the site can run free on a sub-address of a domain already owned, with a second free Resend account registered against it.

6How the appointment system works Unchanged by the hosting decision, confirmed against the built application.

  1. The visitor books inside Calendly. The "Make Appointment" tab shows Calendly's own booking calendar embedded in the page. There is no separate request form and no approval step.
  2. Calendly handles all the booking email. Confirmation, professor notice, reminders and cancellations all come from Calendly. Our site sends none of it.
  3. The admin records the booking in the admin panel by hand. Automatic sync into our database is a paid Calendly feature (Standard, $10/mo); the free plan needs the admin to enter it, roughly thirty times a month.
  4. The admin decides what the public sees. A settings switch controls whether the public "Upcoming Events" tab shows anything. Off by default.
  5. Cancellations flow back as a status change, never a delete, so history stays intact.

This behaviour is identical on Option 2 and Option 3; it lives in the application, not the server. It would also have been identical on Option 1, had Option 1 been reachable.

Why R2 stays, even on a dedicated server

Once a server is dedicated to this site alone, there's a natural instinct to put everything on it: database and files. The database side earns its move: it closes a real gap (backups, the pause rule) that costs $25/mo to close any other way. The file-storage side doesn't earn the same move: R2 already has no cost, no traffic ceiling, and a working integration. Moving files to local disk would only add a second thing to back up, for no visitor-facing gain.

8.1 Vercel: what actually happened

Deployment attempt, 11 August 2026

The repository is connected to two GitHub remotes: a personal one, and culpritteam/web, the organisation the project now lives under. Importing the org-owned repo into Vercel failed: Vercel's free Hobby plan only deploys repositories owned by the individual account doing the deploying. A repo owned by a GitHub organisation requires the deploying account to be a member of a paid Vercel Team.

This is not a line item on Vercel's public pricing page. It's a consequence of who owns the repository, discovered by attempting the import, so there is no screenshot to cite here the way the rest of this section does.
